## Executive summary

This project answers a narrow engineering question: can Julian's own repository history be turned into a private, traceable local coding assistant without losing control of provenance, evaluation boundaries, or deployment behavior?

The pipeline now reaches a verified local artifact. It discovered 60 repositories, matched 3,018 personal commits, retained 8,361 deduplicated training rows from 53 repositories, trained a one-step rank-8 LoRA compatibility adapter against a pinned Gemma 4 E4B checkpoint, converted the adapter to GGUF, and attached it to Ollama as `gemma4-e4b-julian:latest`. The deployment passed a native tool call, performance thresholds, and a real Codex edit-and-test task.

<ReportCallout label="Scope of the result" tone="warning">The deployed model is a one-step compatibility artifact. It proves that the data format, training path, tensor conversion, Ollama runtime, tool calling, and Codex loop work together. It does not prove that the model learned Julian's full corpus or improved general coding quality.</ReportCallout>

Three conclusions are defensible today:

- **The corpus has a real evidence chain.** Repository selection, contribution history, filtering, deduplication, split assignment, token counts, model revision, adapter metadata, conversion revision, and runtime checks all have machine-readable records.
- **The local deployment path works end to end.** The final Ollama model selected a native tool, cleared latency and throughput thresholds, and completed a file-edit task whose test passed.
- **Model-quality improvement remains unmeasured.** The honest held-out evaluation requires a completed selection adapter. That run was interrupted before its first recovery checkpoint, so the site does not substitute the smoke artifact or an estimate.

## Corpus provenance

The source material is repository history, not a folder dump. `fetch_repos.py` discovers every visible, non-fork, non-archived repository allowed by configuration. `stats.py` then walks full Git history with rename detection and matches commits against Julian's configured email identities.

The resulting snapshot processed all 60 discovered repositories and attributed 3,018 commits, 868,278 added lines, and 302,760 removed lines. Net contribution is 565,518 lines; total changed lines are 1,171,038. These are contribution-history measures, not a count of the current checkout.

## Dataset construction

The dataset builder turns eligible files into prefix-and-completion rows while preserving source metadata. It selected 5,455 of 5,501 considered files, produced 9,443 candidate chunks, then removed 533 exact duplicates and 549 near duplicates. The final dataset contains 8,361 rows and approximately 4.97 million lexical tokens.

### Split integrity

Train and validation are assigned at repository granularity. No repository contributes to both sides. The current split uses 48 training repositories and five validation repositories, producing 7,172 training rows and 1,189 validation rows. The built dataset passed its own `datasets.load_dataset(...)` self-test with both split counts intact.

This boundary matters. A row-level random split would let near-identical conventions, modules, or neighboring file regions from the same project appear on both sides. Repository-level splitting is stricter and makes a later held-out result more meaningful.

### Safety and quality filters

The builder rejects configured sensitive paths such as environment files, private keys, credentials, and identity keys. It also applies high-confidence credential signatures, file-size limits, Git ignore rules, generated-directory rules, and supported-extension checks. In this build, 31 sensitive-path hits and one OpenAI-key signature were rejected. That is a precision-oriented safety layer, not a guarantee that the retained corpus is publishable.

<ReportCallout label="Privacy boundary" tone="info">The raw repositories, dataset rows, and adapter weights remain local and are excluded from Git. The website publishes aggregate evidence only. Source licenses still govern every retained file.</ReportCallout>

## Model and adapter

The model target is fixed rather than selected from a retrospective leaderboard. Training uses `unsloth/gemma-4-E4B-it-UD-MLX-4bit` at revision `f29de68cb284ca208446e647b339569935025ef3`, with upstream lineage `google/gemma-4-E4B-it`. The matching Ollama deployment base is `gemma4:e4b`.

Only language-model linear layers receive LoRA adapters. Vision and audio stacks stay frozen. The profile uses rank 8, alpha 16, dropout 0, completion-only loss, gradient checkpointing, a 1,024-token sequence cap, and a learning rate of `1e-5`. The intended full profile uses batch size 1 with four-step gradient accumulation and one complete data pass.

### What did not complete

Selection training was configured for 7,172 iterations over training repositories with validation on the 1,189 held-out rows. It reached iteration 40 and was interrupted with return code 130. Recovery checkpoints are written every 1,000 iterations, so there was no selection adapter to evaluate or resume exactly. The distinct production run, which would merge train and validation data after model selection, was prepared but never started.

## Verified deployment

The MLX adapter cannot be attached directly to Ollama's Gemma 4 base. Deployment therefore validates the MLX package, transposes and renames paired LoRA factors into PEFT Safetensors, converts the PEFT adapter to GGUF with a pinned llama.cpp revision, and creates an Ollama model with a 32,768-token context window.

The final GGUF adapter contains 343 tensor pairs and is 38,926,080 bytes. The conversion uses llama.cpp revision `b15ca938ad00aa6b3ee6c2edda7363fd02826b18`; verification evidence records the source adapter, PEFT metadata, output hash, Modelfile, runtime metrics, and Codex result.

## Personalization

Personalization has two layers with different evidence strength. The LoRA layer is currently only a compatibility gate and should not be treated as learned personal style. The system-prompt layer is explicit and active today.

The persistent prompt identifies Julian Schmidt, his GitHub account `Julian-AT`, his Vienna location, portfolio, primary stack, and representative projects. It instructs the model to be direct, challenge flawed assumptions, inspect before editing, make narrow changes, verify work, avoid speculative abstractions, and keep private facts private. It also prohibits emojis and em dashes in model responses.

The prompt lives in `deployment/system-prompt.txt`. `deploy_ollama.py` reads it from `config.yaml`, rejects an unsafe Modelfile delimiter, embeds it as a multiline `SYSTEM` instruction, and recreates the Ollama tag. This keeps the identity durable across redeployments instead of relying on a hand-edited generated Modelfile.

## Limits and status

This report is designed to be useful because it states where the evidence stops.

- **No completed model-quality evaluation.** The selection adapter did not finish, so there is no defensible held-out comparison against the untouched base.
- **One training step is not personalization.** The deployed LoRA proves compatibility, conversion, and runtime behavior. It does not demonstrate learned preferences or code quality.
- **Repository history is correlated.** Thousands of commits do not imply thousands of independent programming tasks. Repeated frameworks, generated scaffolds, and project conventions reduce effective diversity.
- **Filtering is not publication clearance.** Secret signatures and sensitive paths reduce obvious risk, but they do not settle privacy, copyright, or repository-license questions.
- **Metrics are machine-specific.** Throughput, latency, and peak memory were measured on the local Apple Silicon machine and should not be generalized to other hardware.
- **The Codex gate is a focused integration test.** One edit-and-test fixture proves the agent loop works, not that the model can solve arbitrary software-engineering tasks.

The next scientifically meaningful step is not another deployment screenshot. It is a completed selection run, followed by the fixed held-out evaluation defined in `TRAIN.md`. Only after that result is reviewed should a separate production adapter train on the merged safe corpus.
